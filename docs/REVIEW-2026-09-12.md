## Bugs fixed

1. **`runner.lua` — `run_selection` resolved `poste.indicators` with
   `select(2, pcall(require, ...))`** (dd98342). On a missing module, select
   hands back the ERROR STRING, which is truthy — `indicators.clear_all(src)`
   then indexed a string and crashed the whole selection run. Every other
   call site already used the `local ok, x = pcall(...)` pattern; this one now
   does too.

2. **`session_conn.lua` — `log()` collapsed every level but `ERROR` to
   `DEBUG`** (dd98342). The watchdog's "session stalled; restarting it" notice
   was tagged `WARN` but rendered at DEBUG — invisible in a default session,
   so a stalled session restart was always silent. Explicit level map now;
   per-line stderr chatter deliberately demoted to DEBUG (a chatty process
   must not spam popups — stderr still reaches users via every `execute()`'s
   on_error paths). Pinned by a spec.

3. **`runner.lua`/`buffer_setup.lua` — `<Esc>` never canceled anything**
   (714a2bf). `exec_run.cancel()` existed, was spec-covered, and red line #4
   says the busy state must never stick — but no keymap or command ever
   called it, while BOTH busy notifications told the user to "press <Esc> to
   cancel first". A slow/stuck redis-exec job wedged every later run until
   the process died on its own. Added `runner.cancel_current(buf)` (cancel +
   clear that buffer's running spinners — a canceled run's on_exit is dropped
   by the seq guard, so the spinners can never clear themselves — + notify),
   bound to the new `redis_source` `cancel` keymap (default `<Esc>`), listed
   in `g?` help. Spec pins busy → cancel → spinners cleared → idle no-op.

## Known limitation (recorded, not changed)

**A selection that CONTAINS `USE`/`SELECT` lines runs as one batch against
the context ABOVE the selection; the in-selection directives are silently
dropped.** `run_selection_async` treats the selection as a single-connection
batch (context inheritance resolves the nearest USE/SELECT strictly above
`entries[1]`, per the 09-11 fix), and `run_async` filters non-command entries
out of the payload. So selecting `USE b` + `GET k` runs `GET k` against the
old connection — a file run would have honored the switch. Fixing it means
grouping the selection per-connection (reusing `group_by_connection` +
`dispatch_group`) and reworking the indicator/db alignment for multi-group
selection runs; deferred until someone actually hits it in practice. Selecting
the commands alone (or running the file) gives the correct behavior today.
