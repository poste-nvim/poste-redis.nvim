## Bugs fixed

1. **`exec_run.lua` — a trailing `USE name` with no command under it
   stranded the file run** (3ff3de9). `dispatch_group` handed the
   zero-entry batch to `run_async`, which refuses it ("Nothing to
   execute") and returns *before ever calling `on_done`* — the dispatch
   chain died there: `run_file`'s per-line "running" indicators never
   cleared, no panel rendered, and every later batch of the file was
   dropped. Empty batches are now skipped synchronously and `on_done`
   always fires. Pinned by two exec_run specs (trailing USE; USE-only
   file).

2. **`exec_run.lua` — a selection inherited the file's LAST USE, not its
   own section** (bc3f5c9). `run_selection_async` fell back to
   `_connection_for` (state context, then the last USE anywhere in the
   file), so a cursor run inside the `USE a` section of
   `USE a / GET 1 / USE b / GET 2` executed against b — silently
   cross-connection, and the source winbar (which shows the nearest USE
   above via `context.entries_context`) claimed otherwise. The selection
   now resolves the nearest USE above it (`_use_above`, read-only), with
   the state context as fallback, and `run_async` stamps
   `opts.connection_name` onto results so the panel label names the
   section that ran.

3. **`buffer.lua` — `refresh` re-attached the pre-refresh meta**.
   `out.meta = tab.meta` kept the tab's connection/db/key stamps but also
   the stale `value`/`status`/`latency_ms`/`error`: `K` on a refreshed tab
   previewed the OLD value (`state.last_value` rode `meta.value`) and the
   winbar kept the old latency/status. The meta is now merged (identity
   stamps win) and the four time-varying fields are re-stamped from the
   fresh event.

4. **`parser.lua` — `key_arg` treated `MEMORY`'s subcommand as the key**.
   `MEMORY USAGE user:1` put `USAGE` in the key slot, so `gd` reveal and
   the result tab binding aimed at the subcommand. `MEMORY` joins the
   server-addressing exclusion list (its real key, when any, sits at
   position 3).

5. **`history.lua` — the sidebar's error highlight covered 1 byte of the
   3-byte `✗`**. nvim clamps extmark byte ranges at the char boundary, so
   the `PosteRedisHistoryError` color painted nothing. The mark span now
   rides the extmark span table (this was the 09-10 "carried as cosmetic"
   observation — it was a one-line fix after all).

## Features

- **`<CR>` on a USE line executes the directive** (e1f3b7c). `USE <name>`
  under the cursor switches the connection (notify on success/failure);
  a bare USE opens the connection picker. Previously every cursor run on
  a USE line died with "Nothing to execute". Pinned by two runner specs.

## Cleanups

- **`connections.lua` — `load_dotenv` no longer books a negative cache
  entry**. Reviewing the mail family's sticky not-found cache suggested
  the same bug here; an experiment against the pre-change code proved
  the old `mtime nil == nil` scheme was behaviorally CORRECT (a `.env`
  created mid-session always recomputed, because the found file's mtime
  never equals the cached nil) — the es env_spec already pins exactly
  this. The rewrite just makes the documented "negatives are never
  cached" rule explicit, drops the dead `{}`/nil bookkeeping, and the
  new spec pins the behavior so a future cache rewrite cannot break it.
  Recorded here because the initial commit message overstated the bug;
  the behavior is unchanged.

## Observations (not changed)

- `browser/info.lua:68` uses `handle and handle(ev.value) or (...)` — the
  documented `and f() or f` trap. All four current handlers return
  `v and v.value`, so the fallback evaluates to the same nil today; a
  future handler that legitimately returns `false`/`nil` would silently
  get the raw value. Left alone because the honest `if` form buys nothing
  right now, but any new handler here should rewrite it first.
- `browser/scan.lua` `scan_keys` still bumps a `page` counter it never
  reads (scan_group uses it for render pacing, scan_keys appends every
  page). Dead local, harmless.
- `browser/async.lua` header comment: "this is why header discovery had
  to page at 500" — header discovery pages at `header_scan_count`
  (default 5000) today; the sentence predates the retune. The
  `--max-items` rationale itself is still correct.
- `exec_run._connection_for` documents a "first redis connection in
  connections.toml" final fallback that the implementation does not have
  (no USE + no current context → nil). The docstring over-promises; the
  behavior matches the error path's message, so only the comment is off.
- `runner.run_selection` on a USE line reports "Nothing to execute" —
  technically correct but a cursor-on-USE specific hint would be kinder.
