## Bugs fixed

38. **A rejected browser write left no record at all**
    (`browser/actions.lua`, `browser/grid_edit.lua`, `history.lua`, `9e3a95f`).
    Every browser mutation recorded inside `on_response`; the 13 `on_error`
    callbacks across the two modules only notified, and a notification is gone
    the moment the command line redraws. Meanwhile the *same* command run from
    a `.redis` buffer lands in the history sidebar with a ✗ and stays
    replayable (item 36 is about exactly that entry). So the audit trail
    depended on which door you used, and the browser door had no trail.

    The 13 sites are not interchangeable, which is why this needed a pass of its
    own rather than a sweep. Classified by what the call could have changed:

    | write-side — now records | read-side — creates no entry |
    |---|---|
    | `delete_key`'s `DEL` | `delete_prefix_keys`' estimate `SCAN` |
    | `delete_prefix_keys`' per-key `DEL` | `delete_nodes`' per-group `SCAN` (see 39) |
    | `delete_nodes`' per-key `DEL` | `set_ttl`'s `TTL` pre-check |
    | `set_ttl`'s `EXPIRE`/`PERSIST` | `rename_key`'s `EXISTS` pre-check |
    | `set_ttl_nodes`' per-key `EXPIRE` | `grid_edit`'s `LINDEX` verify |
    | `rename_key`'s `RENAME` | `grid_edit`'s `HEXISTS`/`ZSCORE` probes |
    | `grid_edit`'s `exec` (any cell/row write) | |

    7 record, 6 do not. A refused `DEL`/`RENAME`/`EXPIRE` now pushes
    `status = "error"` with the server's message, so the sidebar shows ✗ and
    `history.activate` can show *why*. The read probes stay silent: recording
    them would put a failure row on the ledger for a command that changed
    nothing, and their failure paths already refuse to dispatch the write behind
    them (spec-pinned for the `EXISTS` and `TTL` pre-checks, the estimate
    `SCAN`, and the list `LINDEX` verify). The `HEXISTS`/`ZSCORE` probes are
    pinned only on their "the name is taken" reply — a transport failure there
    is untested, and reaches the same no-write branch.

    Three of the seven sit inside aggregated batches, where "the write failed"
    is only half true: a per-key `DEL` failure does not stop the loop, so one
    line had to carry the count that survived. `delete_prefix`, `delete_nodes` and
    `set_ttl_nodes` now record `status = "error"` with
    `"<n> of <m> key(s) not deleted: <first error>"` (or `not set` for TTL), and
    their notify says `Deleted 1/2 key(s) …` at WARN instead of `Deleted 2`.
    Before this, a run where 4 of 5 keys survived recorded as five deleted — the
    ledger's only sin is lying about what it did.

    `history.activate` needed the matching half: an entry with no result set but
    an error used to render the "No result snapshot for this entry" hint, which
    reads as if the entry itself had been lost. It now renders the same ERROR
    block a replayed failed command gets (`format.format_error`), and the hint
    stays for a *successful* write, which genuinely has nothing to show.

39. **A batch delete dropped the tree row of a node whose SCAN failed**
    (`browser/actions.lua`, `9e3a95f`). `delete_nodes` SCANs every selected
    group, then deletes the collected keys and `detach_node`s *every* job. If a
    group's SCAN died, it contributed zero keys — and still lost its row. The
    keys stayed in the keyspace while the browser showed them gone, with no row
    left to retry from. Two more things were wrong in the same breath: the
    confirm quoted a key count that silently excluded that node, and the
    aggregated history line said `Deleted 1 key(s) across 2 node(s)` for a
    selection whose second node had never even been counted.

    Now a failed collection is tracked per node (`job.scan_failed`, once per
    node even if a later page of the same walk also dies), the confirm says
    `(N node(s) could not be scanned — their keys are NOT included)`, the
    aggregated line appends `"<n> of <m> node(s) not scanned: <reason>"`, the
    notify says so, and the unscanned node keeps its row. Its `redis-cli --scan`
    pipeline stays in the yank form, which is precisely the retry command.

## Spec-writing note: the callbacks that outlive their test

The new specs initially failed with `history.count()` returning 5 where 1 was
expected. Nothing was wrong in the code: an earlier test's batch chain (SCAN →
`vim.schedule` → DEL → record) was still in flight when the next test's
`before_each` cleared history, so leftovers landed in the fresh ledger. Busted
runs specs synchronously, so those callbacks only fire while some *other* test
is sitting in `vim.wait` — which is why the count depends on which test asks.

Fixed in the new describe block's `before_each`: pump the loop for 150 ms,
*then* clear history and reset the command log. Anything asserting exact
`history.count()` or exact `#calls` across an async chain needs that order; the
older tests in the file are safe only because they assert "≥" or read
`list()[1]`.

## Recorded, not changed

- **The two doors still disagree in the other direction.** A browser write that
  *succeeds* records `kind = "write"` with no result set, so activating it shows
  the hint and `y` yanks an executable form; a `.redis` `DEL` that succeeds
  records the `integer` reply and activates as a real grid tab. That is
  defensible (the browser knows what it meant to do, the buffer only knows what
  the server answered), but it means "replay this entry" and "redo this
  mutation" are different gestures with one key. Not a bug; noted because the
  next person to touch `activate` will meet the same question.
- **`delete_prefix` aborts the whole batch on a failed estimate SCAN** while
  `delete_nodes` proceeds with what it collected. The first is safer (nothing is
  deleted, one notify says why) but the two read differently in the sidebar: one
  shows nothing, the other shows a ✗ row naming what it skipped. Unifying them
  would mean choosing which behaviour is right, and that is a UX call rather
  than a fix.
