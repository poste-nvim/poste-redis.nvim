# Code Review — 2026-09-21

Second pass of the same day over the whole plugin. This one re-read the
modules downstream of the transports: the vendored TOML parser, connection
resolution, the picker/selection layer, the command parser, the runner's
safety gate, every SCAN accumulator, and the history sidebar. Baseline
before the pass: 523 green (`REVIEW-2026-09-20.md`). Rounds 3, 4, 5, 6, 7, 8
and 9 are further passes the same day — the browser's render layer, the winbar's size
report, the two rules this copy had not learned from its siblings (the
`poste` binary lookup and `env.json`), and the startup check that still
carried its own copy of the first of those; the item numbers continue the list
above. Round 7 covers what the earlier rounds left unobservable and
unexercised: the diagnostics that could not say which candidate won, the last
`io.popen` of a configured path, and the Windows extract step. Round 8 is the
Windows bug those rounds left behind: a lookup that tested extension-less names
only, on the one platform where the installer writes `.exe`. Round 9 is the
other half of that startup path — the two downloads that had no time ceiling, and
the checksum compare that rejected a good download on Windows.
Final tally after all of them: 589 Success / 0 Failed / 0 Errors over
32 spec files, luacheck **0 warnings / 98 files** (`luacheck .`; `luacheck lua/
tests/` gives 97).

## Bugs fixed

1. **The vendored TOML parser was two syncs behind its upstream fixes**
   (`lua/poste-redis/toml.lua`, `e583cca`). The copy here was pinned to
   poste-db@`94fccf2` and missed the inline table/array parsing added in
   `cc6652e`; re-copied verbatim to `89f0468`. This matters on a
   redis-only install because a project keeps one `connections.toml` for
   the whole family, whose postgres sections write
   `tunnel = { to = … }` — the old parser survived only because nothing
   here consumes those keys. `89f0468` additionally rejects the shapes that
   used to "parse fine": a `[[connection]]` array-of-tables header became a
   section literally named `[srv`, and a dotted `tunnel.to = "h"` became the
   flat key `"tunnel.to"`, i.e. a connection looked configured and failed
   only when it was used. Specs ported for the new shapes (the
   `tunnel.normalize_cfg` case stays upstream — no tunnels here). Supersedes
   the 2026-09-20 "recorded, not changed" note that array-of-tables is
   unsupported-but-harmless.

2. **`port = "{{TYPO}}"` crashed `resolve()` instead of reporting a config
   error** (`connections.lua`, `363f5b2`). A literal like
   `"{{REDIS_PORT}}"` (typo'd or unset var) reached `string.format("%d")`,
   which raised out of a function whose whole contract is `(url, err)` —
   no caller pcall'd. Fractional/negative `db` had the same shape. Both are
   now returned errors that name the connection but never echo the value
   (`port = "{{REDIS_PASS}}"` would otherwise print a secret into the
   message). The failure was additionally *discarded* by
   `_connection_for`/`_use_above`, so a broken `USE` line reported "no
   connection found" while the line sat right there; the reason is now
   appended. `3de1265` finished the rule: `port` is bounded at 65535 (the
   transport is 16-bit), while `db` stays unbounded on purpose — `databases`
   is a server setting and `SELECT` is where a bad index should surface.

3. **The `connections.toml` cache was dead code** (`connections.lua`,
   `447e37c`). `find_connections_toml` walked every ancestor directory on
   every call and only compared its `path + getftime` cache *afterwards*,
   so completion — which calls it per request — paid a `filereadable()` per
   ancestor regardless. The cache is now checked first; a miss still
   re-walks, so a file created mid-session is still discovered.

4. **Exact large integers rendered (and were yanked) in scientific form**
   (`format.lua`, `a1a4b84`). The "print all digits" bound was `1e15`, but
   a double is exact over integers to 2^53 — so a microsecond timestamp
   (`1.7e15`, one of the commonest integers in redis) displayed as
   `1.75e+15`, and `y` put that into the register. The bound is now
   `util.INT_EXACT = 2^53` in `cell()`, `to_clipboard` and `render_integer`;
   past it scientific form stays, because full digits there would advertise
   precision the decoded value no longer has.

5. **A dangling `RENDERERS.string` entry and an unreachable
   `render_string`** (`format.lua`, `6577214`). Fixing (4) removed
   `render_string` but left the table pointing at the undefined name; the
   function had never been reachable anyway (`GRID_BUILDERS.string claims
   type `"string"` first`), and its twin quoted values without the newline
   escaping `cell()` applies — exactly the divergence that gets edited as
   if it were live. Both, plus the stale module header, are gone.

6. **Every connection picker crashed on installs without snacks.nvim**
   (`select.lua`, `e01011f`). `nvim_buf_set_extmark` rejects the `-1`
   namespace that `nvim_create_namespace`/`nvim_buf_clear_namespace` accept,
   so rendering any item carrying a description aborted `pick_float`
   mid-render: the half-open float stayed visible, and `select()` layered a
   second prompt on top of it because its `pcall` swallowed the error.
   This file is a vendored copy of poste-db's `select.lua`, where the same
   bug was fixed in `cc6652e` — the copy had drifted. Ported that repo's
   spec too (fails on `-1`, passes on a real namespace).

7. **A quoted command head bypassed the dangerous-command blacklist**
   (`parser.lua`, `1f218e8`). `is_dangerous`, the winbar grouping and the
   `USE` connection argument compared the *raw* token, so
   `"FLUSHALL"` / `'flushall'` / `USE "local"` all failed to match even
   though the transport runs them identically. Introduced `head_of(tok)` =
   `unquote(tok):upper()` and routed every interpret-the-head site through
   it, while `entry.raw` keeps the typed text verbatim for display and the
   winbar.

8. **`confirm_commands` was documented but not implemented** (`runner.lua`,
   `2338b2c`). The config row and README promised a confirm on destructive
   commands; nothing in Lua or the Rust binary asked. Added
   `confirm_dangerous(entries)` to `run_selection` and `run_file` — one
   question naming each distinct dangerous command in the batch, default
   **No**, `confirm_commands = false` opts out. The gate lives in the Lua
   runner (not the CLI) for the same reason poste-db puts it in
   `sql_runner`: the binary is a shared transport and has no idea whether
   the caller already confirmed. Documented in the README and in doc-poste.

9. **SCAN accumulators re-added keys the cursor returned twice** (browser
   `scan.lua`/`async.lua`/`actions.lua`/`info.lua`, completion
   `data.lua`, `48eab04`). Redis SCAN is at-least-once: a rehash between
   pages repeats keys, so a prefix delete could `DEL` the same key twice
   (reporting an inflated count), search could list duplicates, and the
   group-info sampler could over-sample. One helper — `util.append_new(dst,
   seen, src)` — now fronts every accumulation, deduping by string value.

10. **An entry with no reported status rendered as `✓` in the history
    sidebar** (`history.lua`, `f5ef991`). The mark chain ended in
    `e.status and "✓" or " "`, but `push()` normalises `status` to `""` — and
    `""` is truthy in Lua, so the blank arm was unreachable dead code and a
    command that never reported a status looked like a success. Now an
    explicit `status ~= ""` comparison.

11. **A broken `connections.toml` was re-read and re-parsed on every
    redraw** (`connections.lua`, `612c227`). `read_config` returned the parse
    error *before* touching the cache, while the success path caches under an
    mtime key — and the statusline and completion read config on every
    redraw and keystroke, so a typo in the file turned each cursor move into
    a file read plus a parse. poste-db's `cached_parsed_config` caches the
    failure the same way; the vendored copy had drifted. The message is kept
    beside the cache so the `(nil, err)` contract still says why.

12. **`port = 0` built `redis://h:0/0`** (`connections.lua`, `69a1e7f`). The
    shared `field` helper bounded `port` above by 65535 and both fields below
    by 0 — correct for `db`, where 0 is the default database, wrong for a
    socket port, so the typo slipped past validation and died in the
    transport. `field` now takes its minimum explicitly (`port` 1..65535,
    `db` ≥0) and the message states the bound (`from 1 to 65535`), matching
    the rule `poste-db` and the Rust store apply to their `port` field.

## Round 3 — the browser tree's render budget

13. **`render_max_lines` capped each branch, not the tree**
   (`browser/tree.lua`, `29f9371`). `flatten_tree` recursed with
   `budget` passed by value: a subtree decremented only its own copy, so every
   sibling branch restarted at the full number. With a budget of 5, a db node
   over two 10-key groups rendered 8 rows. The cap exists because the freeze it
   guards against scales with the size of the whole buffer rewrite (the comment
   above `flatten_tree` says exactly that), and the scans read the resulting
   `last_truncated` to stop paging — both were being fed numbers from a cap that
   silently grew with the tree's width. What the subtree spent now flows back up
   inside `emit_children` (`#child_lines` is exactly its consumption).

   The spec nests two branches on purpose: every pre-existing cap test used a
   flat display root, where all rows share one stack frame and the leak cannot
   show. Reverting the one-line fix fails that test and nothing else.

   Also in this file: `@return flatten_tree` documented four values and returned
   five (`budget_skipped`, the flag that decides whether a trailing notice row
   is appended) — the annotation now lists both.

## Round 4 — the winbar quoted the transport cap as the reply's size

14. **`status_summary` measured what it printed, not what it fetched**
    (`format.lua`, `7caaa44`). For a string reply the size came from
    `#v.value` — the text the binary was willing to put on the line under
    `--max-bytes` — while the authoritative `len` the grid uses was ignored.
    A 50 MB string therefore advertised "len 65536" and read as a complete
    value. The only caller is `buffer/view.lua:update_winbar`, and for a
    string reply the winbar is the whole report — the grid has no rows to
    count. It now compares the two: `len N, truncated` when `len` exceeds
    what is shown, plain `len N` otherwise. Same direction as the binary-side
    fix in poste.nvim round 3 (its `status` field had the identical hole, on
    the wire rather than on screen), which is what made the Lua copy worth
    re-reading.

The tally did not move — the assertions went into the existing
`status_summary` spec, which now pins a truncated string, a non-string reply
and the error path in one block. Gates below are the post-fix re-run.

## Round 5 — the two things this copy had not learned from its siblings

15. **The binary lookup accepted a file it could not run** (`state.lua`,
     `eb1fc20`, pinned by `tests/redis/state_spec.lua`/`92ee7c1`). This is the
     same `find_poste_binary` that exists in poste-db, and the copy here had
     drifted twice over: it tested `filereadable` alone, and it had no
     environment override at all. The first drift is the dangerous direction —
     a downloaded or copied binary without the exec bit (or the test dummy)
     satisfied `vim.g.poste_binary` and won over a working `poste` on `$PATH`,
     so the failure surfaced at spawn as an opaque jobstart error rather than
     "no binary found". All four candidate arms now go through one `usable`
     predicate (`filereadable == 1 and executable == 1`), and `$POSTE_BINARY`
     is read second, right after the in-memory config value: a `vim.g` set by
     `tests/minimal_init.lua` never reaches the child nvim that plenary spawns
     per spec file (that process starts without `-u`), so the environment is
     the only channel CI and those children have. The dummy inherits the new
     rule — it is chmod'ed `0755` now, or the hardened check would hide it
     from the suite that depends on it.
     The spec is new to this round rather than ported: `eb1fc20` landed
     without a test of its own, and two of its four cases fail against the
     pre-fix file (a readable-only candidate comes back as the answer; the env
     fallback returns `(nil)`). The fourth is a guard that cannot fail
     pre-fix — with no env arm there was nothing to check — and exists to stop
     a future one from skipping `usable`.

16. **`env.json` was read by a weaker copy of the CLI's rule**
     (`connections.lua`, `8b027eb` + `1cee45c`). Item 2 of this report is the
     story of one rule with several copies drifting apart, and `docs/schema.md`
     rule 2 states the contract the Rust resolver implements. This file's
     reader of the same name was missing four of its clauses:
     - a nested object became a substitution value, and `gsub` answered
       `invalid replacement value (a table)` — proven against the pre-fix file
       with a headless probe, and it propagates: the three `apply_env` call
       sites are `get_connection_config` (`connections.lua:255`),
       `resolve_redis_url` (`:315`) and the picker's `list_connections_sync`
       (`:357`), and none of those three calls is wrapped in `pcall`;
     - a number or boolean stayed typed, where the CLI renders every scalar as
       text. Measured end to end against `{"dev": {"POSTE_FLAG": true,
       "POSTE_PORT": 6379}}`: before, `get_env_vars` gave `boolean`/`number`
       and a `{{POSTE_FLAG}}` reference aborted the whole substitution with
       `invalid replacement value (a boolean)`; after, both are `"true"` and
       `"6379"` and the URL resolves. (`gsub` happens to accept a number, so
       the number is a type-level divergence and the boolean is the one that
       throws — both are the same clause of rule 2, so both are pinned:
       `vars.POSTE_TEST_PORT == "5432"`, `vars.POSTE_TEST_DEBUG == "true"`.)
       Note the third scalar this file must not put in the table: `null`,
       which the CLI skips;
     - a file with no `dev` stanza (the flat `{"KEY": "v"}` form) yielded no
       variables, while `poste connection list` resolved it as a var map for
       every environment;
     - the reference pattern was `{{([%w_.]+)}}`, narrower than the CLI's
       `\{\{([^}]+)\}\}`, so `{{POSTE_TEST-HYPHENATED}}` stayed literal braces
       on this side and expanded on that one — the picker connects while the
       CLI prints a working URL, which is the worst possible split to
       discover.
     Only string/number/boolean survive into the table now, and as text
     (`scalar_env_vars`, same name and rule as poste-db's), a section that is
     not a table falls back to the whole document, and the pattern is
     `{{(.-)}}`. Four specs in `tests/redis/connections_spec.lua` fail on the
     pre-fix file with exactly the values above (`(table: …) { [team] = 'db' }`
     vs `type nil`, `(number) 5432` vs `'5432'`, `(nil)` vs `'flat-value'`,
     `'{{POSTE_TEST-HYPHENATED}}'` vs `'h1'`).

## Round 6 — the startup check was the last copy of the binary rule

17. **`install_binary.ensure()` duplicated the lookup and drifted the same
     three ways** (`install_binary.lua`, `2c1e164`). Item 15 fixed the resolver;
     this function had its own 47-line walk of the same candidates, and setup
     called *this* one. So `readable` alone decided (`g:poste_binary` pointing
     at a file without the exec bit was returned as the answer and the download
     that would have produced a runnable one was skipped), `$POSTE_BINARY` was
     never read, and `$PATH` was never searched — which made the documented
     "put the binary in your PATH" install fetch a release into
     `stdpath("data")`, and that copy outranks `$PATH` in the resolver, so the
     user's build quietly stopped being used. `ensure()` now asks
     `state.find_poste_binary()` and keeps only what a lookup cannot do: the
     download and its notification. `tests/redis/install_binary_spec.lua`
     covers it — 2 of its 4 cases fail against the pre-fix file, printed as
     `refuses a readable but not executable override` and `uses a binary on
     $PATH instead of downloading a release`; the other two pin the delegation
     contract (returns the resolver's answer, no download) and the fallback
     (exactly one download when nothing anywhere is usable). The specs point
     `vim.env.PATH` at an empty temp dir and stub `install.download`, so a
     developer's own `poste` in PATH cannot decide the outcome.

18. **The README's install section described only the download** (`8ba1dda`).
     Same rewrite as poste-db's: the five-step order, the readable-*and*-
     executable rule, and `$POSTE_BINARY` as the channel that reaches headless
     and CI processes.

## Round 7 — diagnostics, and the last two shells the binary was fed to

19. **`checkhealth` interpolated the binary path into a shell, twice**
    (`health.lua`, `01a3804`). The version probe was
    `io.popen('"' .. binary .. '" --version 2>/dev/null')`. Quoting a path does
    not make it inert as a shell argument, and `binary` here is
    `vim.g.poste_binary` / `$POSTE_BINARY` — configuration, not something the
    plugin wrote. Proven with a headless probe against the pre-fix form: a path
    containing `a"b` gives `sh: syntax error: unexpected end of file` and the
    probe silently reports no version, while a path containing
    `x$(touch /tmp/pwned)` executes the `touch` even though no such binary
    exists (the expansion happens inside double quotes). The `2>/dev/null` tail
    was a second, quieter problem: it only means something to a POSIX shell, so
    under Windows' `cmd.exe` it creates a file named `null` and the probe reads
    nothing. Both probes now spawn argv tables through `vim.system` —
    `state.poste_version()` for the version, the same shape for `--help` —
    which is the rule this review kept hitting from the other side: the CLI is
    invoked as data, never as a command line. poste-db had already moved its
    version probe there; this was the last io.popen of a configured path in
    either plugin.
    `tests/redis/state_spec.lua` pins the new behaviour with a path containing a
    space and a quote — `poste_version()` reads the version from it, where the
    shell form above cannot.

20. **The lookup said *what* it found, never *who answered***
    (`state.lua`, `01a3804`). `find_poste_binary()` returns `(path, source)`
    now — `g:poste_binary`, `$POSTE_BINARY`, `installed release`, `dev build in
    cwd`, `dev build beside plugin`, `$PATH` — and both surfaces print the pair:
    `:PosteRedisInfo` shows `poste_binary: …  (from …)`, checkhealth shows the
    same beside the version. This is the diagnosis Round 6 made possible: the
    installed release outranks `$PATH`, so a stray download defeats the build
    the user is staring at, and before this the only evidence was a path that
    looked plausible. The not-found error also gained `$POSTE_BINARY`, the
    documented channel for headless and CI processes. poste-db's `0a2ec36`
    carries the identical change in its own copy.

21. **The Windows install steps passed their paths to PowerShell unquoted**
    (`install_binary.lua`, `9b233da`). `vim.fn.system` in list form means no
    *shell*, but `powershell -Command` joins its remaining arguments and parses
    the result as a PowerShell *command line*, so `Expand-Archive` received
    `-Path C:\Users\Jane` `Smith\…` for any user whose name contains a space —
    `stdpath("data")` lives under that directory on a default install — and
    `$var` or `;` in the same position were re-parsed rather than treated as
    path text. Both `-Command` sites now build one command line through
    `M.ps_literal()`: PowerShell's single-quoted literal, `'` doubled. The same
    fix landed in poste-db's copy (`b118bb3`); three `ps_literal` specs in each
    repo pin the quoting, since the call sites cannot be exercised on macOS.

22. **`poste-redis.state` had two aliases in the same scope**
    (`connections.lua`, `commands.lua`, `0322f4a`). `local state` next to
    `local redis_state`, both required from the same module, in the file that
    resolves connections and in the `:PosteRedisInfo` callback — so reading a
    call meant knowing which of the two names that line happened to use. Each
    site kept `redis_state`, the name the rest of the plugin uses. A
    `local x = require(...)` inside a function is this plugin's deferred-require
    style and was left alone (`history.lua`'s `local w` is a window id read off
    a deferred require, not a second name for the module).

## Round 8 — the one platform the contract did not cover

23. **The lookup could not see the file the installer writes** (`state.lua`,
    `90d5af8`). Rounds 6 and 7 made `find_poste_binary()` the single owner of
    the rule, and this is the bug that survived all of them: every candidate is
    spelled without an extension — `stdpath("data")/poste/bin/poste`,
    `target/{debug,release}/poste`, `bin/poste` — while `install_binary.binary_path()`
    appends `.exe` on Windows, which is also where cargo puts it. So on that
    platform `ensure()` downloaded a release the next lookup could not find,
    downloaded it again on every startup, and `:checkhealth poste-redis` plus
    the transport reported "no binary" unless `vim.g.poste_binary` named the
    `.exe` by hand. Nothing here runs Windows, so the mismatch stayed invisible
    through seven rounds of reading this pair of files.
    The `usable(p)` boolean becomes `resolve_candidate(p)`, which returns the
    path that runs: `p`, or when the new `state.is_windows` says Windows and
    only that exists, `p .. ".exe"` — so a configured path with or without the
    extension both work, and an exact candidate still beats the guess. Order and
    labels unchanged; the same fix is in poste-db's copy (`2969a41`).
    4 specs in `binary resolution on Windows`. Reverting only the production
    change leaves exactly the 2 that pin the bug red (`finds the .exe the
    installer wrote`, `adds the .exe to a g:poste_binary spelled without one`);
    the other 2 — exact match wins, and no `.exe` matching off Windows — are
    guards against the fix overshooting, and pass before it too.

## Round 9 — the startup download, end to end

24. **Neither release download had a time ceiling** (`install_binary.lua`,
    `3e983aa`). `ensure()` runs from `setup()`, so both fetches sit on the
    editor's startup path, and each was a bare `curl -fL url -o path`. curl
    defaults to a 300-second connect phase and no transfer limit at all, so a
    captive portal or a firewall that answers the SYN and drops the rest froze
    Neovim until the OS socket timeout expired — that reads as a hung plugin
    load, not a failed download, and it happens before any of this plugin's UI
    exists to report it. `M.curl_argv(flags, url, out, max_time)` now emits
    `--connect-timeout 10` plus a per-fetch `--max-time` (20s for the checksum,
    180s for the archive) and keeps argv in list form, the shape Round 7
    established as the reason no configured path can reach a shell. The same
    audit checked the asset names and layout against
    `poste.nvim/.github/workflows/release.yml`: flags, `sha256sum` digests,
    flat archive members and the five matrix names all match.
    `verify_checksum()` also leaked `checksum.tmp` when `io.open` failed after
    a successful fetch; that branch now removes the file like the one above it.
    poste-db's copy carries the identical change (`c804b25`).
    4 specs in `install curl_argv`; `curl_argv` is a pure function of its
    arguments specifically so they can assert on argv with no network.
    Two things this round did *not* have to fix, worth recording because they
    are the traps the sibling repo fell into. The yank specs already stub
    `vim.fn.setreg`, so nothing here asserts against the system pasteboard —
    poste-db's `sql_export_spec` did, and went intermittently red in the suite
    for exactly that reason (its item 29). And `install_binary.lua`'s extract
    step already went through `ps_literal()` from Round 7, so the download
    path had no unquoted shell left in it.

25. **The checksum compare rejected a good download** (`install_binary.lua`,
    `5479f62`). `verify_checksum()` finished with `actual == expected`, where
    `expected` comes from the release's `sha256sum`-generated `.sha256` asset
    (lowercase) and on Windows the fallback hasher is `certutil -hashfile`
    (uppercase). The compare is therefore false for every correct archive on
    exactly the machines that reach that branch — it is chosen because
    `sha256sum`/`shasum` are missing — so the installer reported
    `Checksum mismatch — download corrupted`, deleted a good download and
    retried it at every startup. `M.checksum_matches()` lowers both sides.
    5 specs, mirroring poste-db's (`db5527a`): the uppercase case is the one
    that goes red when the compare is reverted, and the other 4 keep any
    "make the mismatch go away" compare that leans on length or prefix alone
    red. Both this and item 24 were found by reading the installer against
    `poste.nvim/.github/workflows/release.yml` instead of against itself; that
    workflow now carries the asset-name / flat-archive / digest-format contract
    as a comment, and its README points at it.

## Round 10 — the write path's tab, and the renames that ate two entries

26. **A write refreshed whatever tab was on screen** (`buffer.lua`, `cd08ea8`).
    `grid_edit`'s header promises "then the tab refreshes itself so the grid
    always reflects the server", and every write ended with `refresh()` — a
    no-argument call the panel had wired as `function() M.refresh() end`, while
    `M.refresh()` started with `local tab = state.tabs[state.active]`. The tab
    the write came from was dropped on the floor. A response that landed after
    the user switched tabs therefore re-ran *another tab's* command (spending a
    query nobody asked for), wrote its result into the active slot, and left the
    edited grid showing the value the write had just replaced. The window is not
    theoretical: a rename is two round trips, a verified list write is three, and
    `<Tab>`/`gd`/`r` all answer instantly.

    `M.refresh(tab)` now resolves the tab's slot by identity, ignores a response
    whose tab was closed or replaced in the meantime, and confines the render,
    the `last_value` write (it feeds `K`) and the TTL recount to the slot that is
    actually on screen. 3 specs: the slot test pins which tab is replaced *and*
    that `K` still previews the tab on screen, the closed-tab test pins the
    identity guard, and the `grid_edit` test pins that the refresh is handed the
    writing tab. Reverting each half separately turns exactly one of them red —
    `tab = state.tabs[state.active]` fails the slot test, dropping
    `if state.tabs[slot] ~= tab` resurrects a dead tab, dropping
    `if slot == state.active` hijacks the `K` preview, and `buffer_refresh()`
    without the argument fails the `grid_edit` case.

27. **Renaming onto a name the key already used destroyed two entries**
    (`browser/grid_edit.lua`, `de9e87d`). `i` on a hash field issues
    `HSET key <new> <value>` then `HDEL key <old>`; a zset member does
    `ZADD key <score> <new>` then `ZREM key <old>`. When `<new>` already exists,
    the first command overwrites *that* entry's value/score and the second
    deletes the row being edited — one edit, two entries gone, and the only
    signal was the `— OK` notice. `o` was the quieter version of the same
    thing: adding a row whose field/member exists silently replaced the other
    row's value.

    Both now probe first and refuse with the row that should have been edited
    instead: `guard_name_free` runs `HEXISTS` for fields and `ZSCORE` for
    members and only then dispatches the write, on the same transport and with
    the same `owner = "browser"` marking the `LINDEX` verification in front of a
    list write already uses — so probes stay out of the command history.
    `name_taken` reads the two reply shapes apart (integer 0/1 versus score-or-nil)
    rather than guessing from one. 5 specs; deleting the `return` inside the guard
    turns the three refusal cases red. `add_row` on a set keeps its behaviour:
    `SADD` of an existing member is a no-op, so nothing is overwritten and there
    is nothing to refuse.

28. **`dd` on a string key asked about the wrong thing** (same commit as 27).
    The confirm read `Delete row  hello  from user:1?` and then ran `DEL user:1`
    — the whole key. A string grid has exactly one row, so the question now says
    what the command does: `Delete the whole value of  user:1  (DEL)?`. One spec
    answers `No` and asserts both the wording and that nothing was sent.

## Recorded, not changed (with rationale)

- **The config caches fingerprint on `getftime`, which is second-granular** —
  a `connections.toml` rewritten twice inside one second can be served from
  the stale parse (`connections.lua:207`). Adding `getfsize` to the
  fingerprint closes most of the gap, but hand-edits can't be that fast and
  the whole family shares this idiom, so a change belongs in all three
  plugins at once rather than here.
- **`completion/data.lua`'s `key_cache` is unbounded** — it grows with the
  number of distinct prefixes completed in a session. Realistically tens of
  entries × `completion_max_keys` strings; a cap needs an eviction policy
  and the scan cost of getting it wrong is one round-trip. Revisit if
  anyone reports memory growth in long sessions.
- **`session_conn`'s watchdog can fire `on_error` twice for one request** —
  the generation guard makes the second dispatch a no-op in every caller
  reviewed, so the double is benign; a stricter guard would need the
  request lifecycle modelled explicitly rather than by generation counter.
- **The `runner` gate covers `<CR>`/`:PosteRedisRunFile`, not the browser.**
  Browser mutations already have their own per-action confirm (delete
  prefix, node delete), and `:PosteRedisRun` of a `FLUSHALL` line is the
  path a user typing it expects to be asked about. Deliberate scope.
- **`dml_guard`'s backslash-escape heuristic** (shared with poste-db) still
  treats `\` as an escape outside strings, which is not standard SQL. See
  poste-db `REVIEW-2026-09-21.md` for the full reasoning.
- **`result/header.update` ignores a changed anchor window.** The float is
  anchored with `relative = "win"` when it is created and the cache-hit test
  compares header/leftcol/width/highlights but not `win`, so re-rendering for a
  different window of the same buffer leaves it painted over the old one. It
  cannot bite today: the float buffer is a scratch buffer with `bufhidden =
  wipe`, so it dies with its window and every teardown-then-reopen takes the
  recreate path (which re-anchors). Recorded because the guard is one `~=` away
  and the next person to render the panel in two windows will find it the hard
  way.
- **Two connections can share a statusline highlight group.**
  `statusline.get_ctx_color` names the group `"PosteRedisCtx" .. name` with
  `[^%w_]` folded to `_`, so `cache-a` and `cache_a` collide and the second
  definition wins. Only reachable with two differently-colored connections
  whose names differ by a punctuation character, and the fingerprint cache is
  keyed by the real name, so it re-applies on every alternating statusline
  evaluation — visible, just not worth a name mangling scheme for.
- **Sibling plugins still carry the vendored bugs fixed here.**
  poste-es.nvim's `select.lua:145` still passes `-1` as the extmark
  namespace, and its `toml.lua` (128 lines, sourced from poste-db@`b7aefc6`)
  is two syncs behind — it predates both the literal-string backslash/BOM
  fix and `89f0468`'s "error on shapes that silently misparse". Out of this
  pass's review scope; `e01011f` and `e583cca` port by copy. The same three
  installers still have the unbounded startup `curl` this round removed:
  `poste-es.nvim/lua/poste-es/install.lua:72,132` and
  `poste-for-{db,mq}/lua/poste/install.lua:67,113`.
- **A write that lands after the user pressed `r` has its refresh dropped.**
  Round 10's identity guard refuses to place a result into a slot whose tab has
  been replaced, which is exactly what happens when `r` refreshes the tab while
  the write is still in flight. That is benign rather than lossy: the write is
  dispatched first, redis serves one connection FIFO, so the `r` re-read already
  saw the new value. The guard costs one redundant refresh and buys back the
  case where the tab is gone.
- **Renames are two commands, not a transaction.** `HSET`+`HDEL`, `ZADD`+`ZREM`
  and `SREM`+`SADD` each have a window where a dropped session leaves the key
  holding both the old and the new entry. `MULTI`/`EXEC` would close it, but the
  transport models one command per request and every caller's error handling
  assumes that; the failure mode is a duplicate row that the next `r` reveals,
  which is recoverable. Recorded rather than re-architected.
- **A refresh drops the tab's column sort but keeps its page and cursor.**
  `M.refresh` copies `page`/`cursor` from the old tab onto the fresh result and
  cannot copy `sort`/`rows_base`, since the fresh rows arrive in server order and
  the record the cursor was on is no longer identifiable by anything but its
  value. Re-applying the sort would mean re-finding that record by content, which
  is what `sort.toggle` does for a re-order of rows it already holds. A surprise
  on the rare sorted-then-refreshed path, not a wrong result.
- **`sort.toggle` follows the focused row by comparing index cells**
  (`r[1] == focused[1]`, `buffer/sort.lua:95`) where it could compare row
  identity — `M.apply` shares the row tables, so `r == focused` is exact. Every
  grid builder numbers its rows 1..N, so no two rows can collide today; recorded
  as the cheaper form for whoever adds a grid whose first column is data.
- **The probes are an extra round trip per rename or add, and `o` on a string
  key still replaces the value without asking.** One `HEXISTS`/`ZSCORE` before a
  write is the same price the list path already pays for `LINDEX`, and on a
  local session it is invisible. A string grid has one row, so "add a row" *is*
  "replace the value"; the prompt names the verb (`Value to SET on k:`) and the
  write keeps the TTL, which is the surprising part worth leaving as-is.
