## Bugs fixed

29. **`escape_for_line` returned `gsub`'s count as a second value**
    (`lua/poste-redis/util.lua`, `3e6fcc0` — recorded here after the fact, as
    the round 10 doc had already been committed). Every sibling helper in that
    file wraps its `gsub` chain in parens; this one did not, and `cell()`
    returns it directly, so it handed back `(string, count)`. A text line built
    as `{ cell(v) }` (`render_integer`, `render_unknown`, and the plain-value
    fallback in `format_result`) got a phantom second line, and anything
    writing lines into a buffer received a number where it expected a string.
    It surfaced while pinning the reply shapes the binary can now emit: an
    integer arriving as a digit *string* rendered as its digits plus a stray
    `0`. The same commit pins the other two shapes that were only implied
    before — a binary field shows its `(binary) N bytes hex: …` marker in a
    hash row rather than `(nil)`, and RESP3 typed scalars (number / boolean /
    wide integer) render as their value on exactly one line. 2 new `it`
    blocks, 3 more assertions inside existing ones.

30. **`key_arg`'s non-key head list missed SCAN, KEYS and EVAL**
    (`lua/poste-redis/parser.lua`, `42a8c72`). `key_arg` answers "does this
    command name a key?" for three visible things at once: the `gd` reveal
    (`buffer_setup.lua` and the panel's `reveal_current`), the result tab's
    `meta.key`, and the winbar's best-effort `TTL <key>` probe. Its denylist
    had 14 heads, all of them "server administration" — so anything whose
    second token is something else was a false positive, including the two
    most common reads in redis:

    | command | `meta.key` before |
    | --- | --- |
    | `SCAN 0 MATCH users:*` | `0` (the cursor) |
    | `KEYS user:*` | `user:*` (a glob) |
    | `EVAL "return …" 1 k` | the whole Lua body |
    | `SUBSCRIBE news` | a channel name |
    | `CLUSTER KEYSLOT user:1` | `KEYSLOT` |
    | `AUTH admin s3cret` | a username |

    A wrong reveal is a wrong tree jump; the tab binding made it a *write*.
    `grid_edit.key_context` needs only `meta.key` plus the reply's type name,
    and `add_row` then dispatches on it: `RPUSH` for a list reply, `SADD` for
    a set, and `SET <key> … KEEPTTL` for any type it does not name — which
    `format.lua` still renders as a grid (`string`, `map`). So `o` on a `KEYS`
    or `SCAN` result aimed a write at a key named `user:*` / `0`, and on a
    script-body tab at a key named after the script. The confirm prompt does
    name the key, but only to whoever reads it.

    The fix is a `NOT_KEY_HEADS` set of 44 entries grouped by argument
    *shape* — cursor-first, body/name-first, channel, key-count-first
    (`LMPOP numkeys key …`), key-at-a-later-position (`OBJECT ENCODING key`),
    administration, handshake/server-to-server — with the counter-examples
    written next to it: `HSCAN key 0`, `BLPOP key 5`, `SORT key BY …` and
    `XRANGE key - +` must stay key-bound, because their key *is* the second
    token. The 14 heads the old chain had are all still there, unchanged.

    9 specs. 8 of them live in `parser_spec.lua` and 6 were red before the
    fix — each one named in the failure output by the token it wrongly
    returned (`0`, the Lua body, `news`, `BLOCK`, `KEYSLOT`, `user:*`). The
    9th is at the layer where the write happens: a `KEYS`/`SCAN` result tab
    has no `meta.key`, while `HGETALL user:42` in the same render keeps its
    binding. Against the pre-fix parser that case measures `user:*`; the
    positive assertions in the first spec exist to keep the fix from becoming
    an over-exclusion that silently disables grid editing.

## Round 12 — cells whose text only stands in for a value

Baseline 611 (round 11's final), after this round **622 / 0 / 0** over the same
32 files, luacheck still clean. 11 new `it` blocks: 3 in `util_spec.lua`, 7 in
`result_grid_spec.lua`, 1 in `format_spec.lua`. On the other side of the
transport: poste.nvim `c8410e1` (test) and `0161a3b` (fix), 127 → 128 `cargo
test -p poste-exec --lib`.

31. **A grid write could target a name that only exists on screen**
    (`browser/grid_edit.lua`, `58a090e`). Every write here sends the cell's
    text as a command argument, and for bytes the NDJSON boundary cannot carry
    that text is a rendering: `key_display` turns a non-UTF-8 hash field or
    zset member into `hex:ff fe`, and a set member — which arrives through the
    *value* path — into `(binary) 2 bytes hex: ff 00`. Measured against the
    pre-fix editor, with the failing command in the assertion output:

    | on a display-only name | what ran |
    | --- | --- |
    | `i` on a hash value cell | `HSET user:1 hex:ff fe edited` — a second field, the binary one untouched |
    | `i` on a zset score | `ZADD user:1 100 hex:c3 28` — same, as a member |
    | `i` on a set member | `SREM … (binary) 2 bytes hex: ff 00` then `SADD user:1 plain` — removes nothing, so the set holds both |
    | `dd` | asked "Delete row hex:ff fe …", then `HDEL`'d a name that never existed |

    The asymmetry is what makes it worth refusing rather than warning: a delete
    that matches nothing answers **OK**, so the panel reports success, refreshes
    and shows the row unchanged; an edit adds an entry whose name is a
    rendering. `util.is_hex_display` recognises both markers and
    `display_only_name` refuses before the prompt (and before the delete
    confirmation), naming the reason and the way out. Lists stay editable —
    their writes are index-addressed and verified with `LINDEX` — and so does a
    hash row whose *value* is binary, because its name still addresses it.
    `hex:zz` and `id:7` stay editable (spec), since the pattern wants whole hex
    pairs joined by single spaces. A field genuinely named `hex:ff fe` is now
    uneditable through the grid: the marker is text, so no rule tells them
    apart, and refusing costs an editor while guessing writes to the wrong row.

32. **`i` on a truncated string stored its own prefix** (`58a090e, same guard`).
    Unrelated to binary and the more likely of the two to be hit: a value
    beyond the transport's byte cap reaches Lua as its head plus
    `truncated = true`, and `edit_cell` prefills that prefix, so accepting the
    default ran `SET user:1 0123456789! KEEPTTL` and cut a 4 KB value down to
    eleven bytes. Refusing is the honest option — the rest of the value is not
    in Neovim's memory to write back. The flag is the one the panel already
    shows: `status_summary` (`format.lua:272`) renders `len <total>, truncated`,
    and the cap is `preview_max_bytes` (config). The escape hatch is the `F`
    that already exists: `browser/value.load_full` re-runs the `GET` with a
    64 MiB `--max-bytes` and renders a fresh tab, which carries no
    `truncated` flag, so the guard lifts there by itself.

33. **A zset score at infinity displayed as `(nil)`** (poste.nvim
    `0161a3b`, pinned from this side by `544b8a6`). `json!(f64::INFINITY)` is
    null in serde_json — the same trap `08acb28` had just fixed for SQL float
    cells, still open in the redis path, in both the zset score and the RESP3
    `Double` scalar arm. It is ordinary data: on a live 8.4 server started for
    this measurement, `ZADD z inf m` is accepted and `ZSCORE z m` / `ZRANGE …
    WITHSCORES` answer `inf`. The executor now emits Redis's own spelling
    (`number_json`), which is also what `ZADD` takes back, so a member rename
    forwards `inf` unchanged — the new `result_grid_spec` case asserts exactly
    that command, and the `format_spec` one asserts the score column keeps the
    text and its right alignment. The two `0.0` score fallbacks became NaN for
    the same reason: an unreadable score shown as a plausible zero is a lie the
    user then writes back.

## Round 13 — the same rendering, one level up: the whole key

Baseline 622 (round 12's final), after this round **633 / 0 / 0** over the same
32 files, luacheck still clean. 11 new `it` blocks, all in
`browser_actions_spec.lua`, 10 of them red before the fix.

34. **Every key-level write sent the key name's rendering**
    (`browser/actions.lua`, `ef116fb`). Item 31 fixed this for a row *inside* a
    value; the tree had the same hazard for the key itself, and SCAN hands key
    names through the *value* path, so a non-UTF-8 key reaches Lua as
    `(binary) N bytes hex: ff 00` and each action then used that text as the
    key:

    | action | what the server saw | what the panel said |
    | --- | --- | --- |
    | delete a key row | `DEL "(binary) 2 bytes hex: ff 00"` → `0` | `Deleted … (0 key(s))`, then detached the row |
    | edit its TTL | `EXPIRE … 60` → `0` | `TTL set on … (60)` |
    | rename it | `RENAME … new` → error | `RENAME failed: ERR no such key` |

    All three replies measured on a live 8.4 server (port 6399, persistence
    off, shut down afterwards) against a name that exists only as a rendering.
    The TTL path even asked the server first, so its prompt read
    `current: -2` — redis's "this key does not exist", shown as a number the
    user has to interpret rather than as a reason to stop. Only RENAME reported
    the truth outright, because it is the one command that errors on a missing
    key; a delete that matches nothing is a success, and the detach that
    follows deletes the *row*: after that delete and a refresh the key was
    still on the server and gone from the screen.

    `refuse_display_only` now gates `delete_key`, `set_ttl` and `rename_key`
    before their prompt, and `delete_prefix_keys` (shared by `delete_prefix`
    and `delete_node`) before its estimate SCAN — that path's count comes out
    of a `MATCH` that cannot hit the real bytes, so it confirms "Delete node …
    (no keys under it)?" and then detaches the folder. The two multi-select
    batches (`delete_nodes`, `set_ttl_nodes`) drop the unaddressable nodes and
    report one line naming the count, rather than refusing the whole selection.
    Same conservative trade-off as item 31: a key genuinely named `hex:ff fe`
    is no longer manageable from the browser, and the over-fire spec pins that
    `hex:zz`, `hex:ffzz`, `binary:key` and `id:7` still are.

## Recorded, not changed (with rationale)

Cumulative over the three rounds; each bullet says which one found it.

- **(round 11) A denylist is not the principled answer to "which token is
  the key".** The server knows: `COMMAND INFO`/`COMMAND DOCS` carries each command's key
  specs (first-key index, last-key index, step, and the `flags` that mark a
  command as having no keys at all). This round extended a hand-maintained
  list because that list is what the code reads today, and because the
  alternative needs a `COMMAND` round trip, a cache of its reply, and a
  decision about what to do for a command the server does not know. Worth
  doing when the panel starts offering more per-command behaviour than "is
  there a key here" — the same reply would also feed the danger blacklist and
  arity hints, which are two more copies of "what does this command take".
  What is recorded instead is the shape of the list, so the next head added
  goes into a group rather than a growing `or` chain.
- **(round 11) `add_row`'s `SET` branch is a fallthrough, not a decision**
  (`browser/grid_edit.lua:365-374`). `local verb = type_name == "list" and
  "RPUSH" or type_name == "set" and "SADD" or "SET"` means every reply type
  outside the named set writes a *string*, overwriting whatever the key held —
  which is right for a `string` grid and wrong for anything unexpected. The
  reachable types are known (`GRID_BUILDERS` in `format.lua` lists exactly
  six), so nothing misroutes today, and item 30 removed the path where the
  key itself could be a non-key. An explicit type → verb table with a refusal
  for unnamed types would be the strict form; it is one more
  "the panel decides what a redis type name means" list to keep in sync, so it
  stays recorded.
- **(round 11) The vendored picker's float fallback shows `height - 2` items
  at most.** `select.lua:88` sizes the window as `math.min(24, #items + 2)`, `render`
  writes every filtered item as a line, and `focus_search` keeps the cursor on
  line 1 — so past ~22 matches the rest is in the buffer but off-screen, and
  `j`/`k` move the ▶ marker rather than the view. Two call sites, both
  connection lists (`connections.lua`), and snacks is the primary path when it
  is installed; without it a 30-connection shared `connections.toml` is
  pickable only by searching. Recorded rather than rewritten: the fix is a
  scroll offset inside `render`, not a new picker.
- **(round 11) Three sibling copies of this picker, none of them identical.** `diff -q`
  against `poste-es.nvim/lua/poste-es/select.lua`,
  `poste-for-db/lua/poste/select.lua` and `poste-for-mq/lua/poste/select.lua`
  — all three differ from this file. Round 10 already recorded the same drift
  for `toml.lua` (where a sibling carried a fixed bug). Copies are deliberate:
  a redis-only install must not need a sibling plugin. The cost is that every
  fix here, including this round's, is a port somebody has to remember.
- **(round 12) The hex marker is a two-repo convention with nothing linking
  the sides.** `key_display` and the binary value shape in poste.nvim's
  `redis_executor.rs` write `hex:…` for a name (≤16 byte pairs) and
  `(binary) N bytes hex: …` for a value (≤64 pairs); `util.is_hex_display` is
  the only reader of that text, and it pattern-matches prose. Each side pins
  its own copy — the Rust `non_utf8_names_are_display_only_hex`, the Lua
  `util_spec` — so a reword fails *somewhere*, but not at the pair: change the
  string on the emitter and the guards added in rounds 12 and 13 stop firing
  silently, which restores the wrong write rather than breaking a test. The
  reply has room for the honest version (`"display": "hex"`, read by
  `format.lua` and by both guards), and it would also carry what the caps mean:
  a 40-byte name shows 16 of its bytes, so even a byte-safe transport needs to
  say "preview". Not done here because it is a transport change for a guard
  that works today.
- **(round 12) The NaN score fallbacks cover a reply the server will not
  send.** A zset cannot hold an unparseable score — `ZADD` rejects it ("ERR
  value is not a valid float", measured) — so `unwrap_or(f64::NAN)` guards a
  malformed or future shape, not today's data. NaN over `0.0` on purpose: a
  score that reads as a plausible zero is the one the user then writes back.
- **(round 13) A rendering also cuts the tree in the wrong place.** Every
  grouped view buckets a key name at its first `:`, and `(binary) 2 bytes hex:
  ff 00` has one *inside* the marker. Measured by building a tree from that key
  list: flat view keeps one leaf with the whole text, while flatten and nested
  both produce a folder named `(binary) 2 bytes hex` with the leaf under it.
  Expanding that folder re-SCANs with `MATCH \(binary\) 2 bytes hex:*`
  (glob-escaped, `scan.lua:580`), which cannot match the real bytes — so the
  grouped views show a folder that empties on open, and their leaf is there
  only until someone expands what stands over it — which is why item 34's
  guard is worth having in every view. Note too that the folder's prefix is
  the marker without its payload, and `is_hex_display` answers false for it
  (checked), so `delete_prefix` there is not refused — it reports "Deleted 0
  key(s) under …", which is at least true.
  The shape of the fix is one shared "first `:` segment of this name" helper —
  five sites do the split today (`scan.lua:70, 205, 283, 331, 523`) — that
  keeps a rendering in one piece; that is a tree-layout change with sort and
  fold invariants, not a guard, so it stays recorded. The cause underneath all
  of this is the transport, which cannot carry a name that is not UTF-8.
- **(round 13) Yank still hands over the rendering.** `yank_key` copies
  `(binary) …` to the clipboard with no notice. Kept: it sends nothing, and the
  text is what the row already shows — a notice there would be about a display
  limit, not a wrong write, and the write-side notices are the ones that have
  to be loud.
- **(round 13) `map` renders a grid the grid guard does not gate.**
  `GRID_BUILDERS.map = build_hash_grid` (`format.lua:147`), while
  `display_only_name` in `grid_edit.lua` names hash / zset / set. Harmless
  today only because nothing emits that type: the executor's Map arm answers
  `"type": "hash"` (`redis_executor.rs:499`), and the sole `map` replies in the
  tree are fixtures in `value_spec.lua`. Same fallthrough shape as round 11's
  `add_row` bullet — a `map`-typed reply would edit binary names unsafely — so
  this is the list to update if the transport ever starts naming one.
