# Code Review — 2026-09-18

Follow-up to `REVIEW-2026-09-17.md`. Scope: the write paths (grid_edit,
browser/actions, runner/history hand-off), the session transport
(mirrored against poste-db's copy), completion/data, and a fresh read of
parser/exec_run. Baseline: tests green (501 → 504 with this pass's
additions), luacheck 0 warnings / 91 files.

## Bugs fixed

1. **History entries dropped the result's `db`** (`runner.lua`) —
   `present()` pushed `command/connection/status/latency/lines/value`
   but not `db`, so a replayed history entry rendered as a real tab with
   `meta.db = nil`. Grid edits, `r` refresh and the winbar TTL probe all
   steer the shared session with `opts.db` — with nil they ran UNSTEERED
   on the session's CURRENT database: a silent wrong-db write after
   replaying a tab that ran on `SELECT 2`.

2. **A chansend-failed SELECT poisoned the session** (`session_conn.lua`)
   — the SELECT send was `pcall`'d with the result ignored. When the
   channel is dead (job died before `on_exit` ran), the SELECT's pending
   entry was never answered: 10 s later the stall watchdog "recovered" by
   restarting a possibly healthy session, and the command behind the
   SELECT would have run unsteered on the old db. The request now fails
   immediately, the pending entry is dropped and the db bookkeeping
   reverts (spec covers the dead-channel case).

3. **Completion's key-prefix SCAN did not glob-escape the prefix**
   (`completion/data.lua`) — a typed prefix like `a*b` matched glob-wise
   and the literal filter below then dropped the extras, so keys
   containing `*?[]\` completed incompletely. Same `util.glob_escape`
   discipline as the browser scans now.

4. **`connections.list_connections_sync` was only reachable through
   `_test`** — health.lua (production code) read the test backdoor. The
   sync variant is a first-class `M` function; the async wrapper and
   `redis_connection_names` delegate to it.

## Recorded, not changed (with rationale)

- **`exec_run.run_sync` has no busy guard** — `run_info`-style calls can
  start a one-shot `redis-exec` while a <CR> batch is in flight. They are
  separate processes against the same server, so at worst two results
  race into the UI; the sync path exists precisely because it must not
  touch the busy state.
- **completion/data `ensure_key_candidates` registers no session owner**
  — a `release("browser")` / `cleanup_buf` can stop the session the SCAN
  rides on mid-flight; the request then fails through `on_error` and the
  completion menu just comes up empty. Registering a "completion" owner
  would pin sessions for every keystroke — not worth it.
