## Change (with tests)

- **`SLAVEOF`/`REPLICAOF` joined the dangerous-command blacklist.**
  Retargeting a replica makes it wipe its dataset and re-sync from the
  new master — the loss lands on the server while the panel shows
  nothing, and a typo'd host in a session buffer is easy to send
  before noticing. All four consumers read the one table
  (`DANGEROUS_COMMANDS`): the panel's yellow flag, the runner's
  confirm gate, `parser.is_dangerous`, and the AI command guard — so
  the change is one entry per name, and AI-generated `REPLICAOF` is
  guarded by the same stroke. `KEYS`/`DEBUG` stay out on purpose:
  blocking or invasive, but constant reads in a dev workflow — a
  confirm on each would train the reflex to dismiss the dialog. README
  and the `confirm_commands` doc comment name the new pair.

## Probed through the real binary, held

- **The failed-SELECT contract `session_conn`'s revert depends on.**
  `SELECT 5` then `SELECT 999` (out of range): the session answered
  the error **and stayed on db 5** — the next `PING` ran there. This
  is exactly what the Lua revert assumes (`session.db` back to the old
  value, next `execute` re-issues the SELECT); had the binary switched
  on a failed SELECT, every later command would run on the wrong db
  under a correct-looking UI. Held.
- **Hostile session stdin** — duplicate seqs are echoed verbatim (Lua
  assigns them, so collisions are Lua's bug to never make), a request
  with no `command` array errors with its seq, `not json` errors with
  seq 0 (never a Lua seq, so a stale pending can never eat it), an
  empty command errors — the loop keeps serving every later request.
  No desync, no park.
- **`--max-items 3` truncation flags**: `truncated: true` with the
  real `len` on list/zset replies — the shape `DEFAULT_MAX_ITEMS`
  (100k) exists to keep out of the browser's way.
- **SCAN reply shape**: `value.cursor` a JSON *string*, keys in
  `value.value` — re-confirming the round-15/16 pin the browser's
  `new_cursor == "0"` compare terminates on.

## Read, held (the sweep that found nothing)

- `browser/scan.lua` — the epoch guards, the `last_truncated` reset
  (an unrelated tree's render cap must not stop this scan), the
  spine-fold cap, and the per-page incremental bucketing all close the
  races they claim to; the only reachable data loss is the documented
  one (rows beyond the render cap are never materialized, on purpose).
- `exec_run.lua` — the db renumber past an injected SELECT survives a
  *user* SELECT as the first real entry (payload indices, not entry
  indices); the dispatch chain's while-loop keeps 10k failed USEs off
  the stack; the failed-start branch delivers `on_error` once and an
  unguarded `on_done` so the caller chain unwinds.
- `browser/grid_edit.lua` — every rename that could clobber probes
  first (HEXISTS/ZSCORE/SISMEMBER), list writes verify through LINDEX
  before LSET, hex-rendered names refuse to go back as text, and the
  truncated-string SET is refused before it can store a prefix as the
  whole value.
- `connections.lua` / `history.lua` — port/db validation, the
  URL-host bracketing, userinfo stripping before host extraction, and
  the sidebar's byte-span extmarks (multibyte mark, pinned time) all
  match their comments.

## Probe artifacts, not bugs

- `util.clean_nil` recurses forever on a cyclic table. Unreachable:
  it only ever sees `vim.json.decode` output, and JSON cannot express
  a cycle. Recorded so nobody "fixes" it with a depth cap the data
  cannot need.
- `util.append_new` walks `ipairs`, so a page with an embedded `nil`
  would silently stop — `vim.json.decode` yields `vim.NIL`, not `nil`,
  so a decoded array is always dense. Same class: unreachable from the
  transport.
