## The thread: a key with a real newline

`SET "a\nb" x` is legal — the tokenizer decodes `\xHH`/`\n` escapes, and
the binary receives the decoded bytes. Every surface that then ECHOES the
key assumed single-line text:

- **`util.render_command` quoted such tokens but let the raw newline
  through inside the quotes** (`db80ee3`). The history sidebar's command
  line then hit `nvim_buf_set_lines`, which rejects embedded newlines.
  Control chars now escape as `\n` / `\r` / `\t` / `\xHH`, mirroring the
  Rust `display_command` shipped in poste.nvim `9580f44`; the escapes
  round-trip through the parser's `unquote`. A literal `\` + `n` pair is
  NOT re-escaped into a newline (the backslash doubles first).
- **`format.format_error` spliced the command verbatim into the error
  block** (`db80ee3`): a failed command on such a key crashed the panel
  render instead of showing the error. The command now goes through
  `escape_for_line` (newline shows as ⏎), which also shields against
  echoes from an older binary.
- **The binary's own echo was a bare `tokens.join(" ")`** — fixed on the
  poste.nvim side (`9580f44`): `display_command` emits the redis-cli
  quoted form so the panel's RE-PARSE (tab refresh, history replay, `gd`)
  recovers the key instead of silently splitting it into `a` and `b`.
  Until a rebuilt binary ships, the Lua-side escapes keep every render
  path single-line.

## Other fixes

- **`parser.key_arg` treated `PING`/`ECHO`'s message argument as a key**
  (`db80ee3`). The `gd` reveal and the winbar's best-effort TTL probe both
  sent it to the server as a key name. Both heads join `NOT_KEY_HEADS`.
- **`browser/searchbar`: Ctrl-J no longer splits the bar** (`565e727`).
  Insert-mode `<NL>` was unmapped, so it inserted a real newline into
  buffer line 1 — the bar region grew a line, every node's line map
  shifted until the next render, and commit (which reads line 1 only)
  silently dropped everything typed after the split. `<NL>` now rides
  with `<CR>` through commit and is deleted with it.

## Recorded, not changed

- **An injected SELECT that the server rejects is swallowed silently.**
  `exec_run.run_async` prepends the file's db SELECT and drops its result
  to keep callers entry-aligned; a rejected `SELECT 99` therefore runs
  the batch on db 0 while the user never learns their SELECT failed (the
  tabs stamp db 0, which is at least what actually ran). Surfacing it
  would need a side-channel notification that does not consume a result
  slot — a design decision, not a patch.
- Still spec-less: `ui`, `winbar` (thin vim-API layers), and the
  `buffer/search.show()` input path.
